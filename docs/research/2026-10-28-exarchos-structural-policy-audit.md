# Research: Exarchos structural policy audit, and what to export to the org

**Date:** 2026-10-28
**Status:** research. Phase 1 starts in the same pull request (org PR template and the `pr-body` action).
**Subject:** [`lvlup-sw/exarchos` at `8a047d8c9`](https://github.com/lvlup-sw/exarchos/tree/8a047d8c9d56c6bf34fc12a6f358f939cf689774). Every Exarchos path below links to that commit.
**Thesis:** export Exarchos's guard proofs, not its rules.

## Summary

Exarchos (lvlup-sw/exarchos at main `8a047d8c9`) enforces its policies through well over a hundred structural guards. They cover comments and prose, instruction files, types, tests, layering, contracts, the gates the product imposes on consumer repos, and CI/release. One required status check, `CI Gate`, rolls them up. The individual rules are mostly Exarchos vocabulary. The asset worth exporting is the discipline the guards use to prove themselves. Each guard asserts a denominator, so it proves it looked. Each runs a seeded violation through the same scanner, so it proves it can fail. Each reports "could not judge" (exit 2) apart from "violation" (exit 1). Each records every exception as typed data with an owner and an expiry, and stale entries fail. On top of that sits a meta-layer that proves each gate is reachable from CI and that its failure reaches the merge decision. The discipline is not applied evenly. Most of the older (Apr–Jul 2026) grep gates lack it, and this audit found four blocking CI gates passing while checking nothing: `withSession` idempotency, measured premises, duplicate suites and the consolidation manifest. The product side has its own weak spot. Review approval and PR creation still trust state fields that an agent can write. So the recommended path has three steps. First, fix about eighteen ranked defects in Exarchos. Then lift the language-neutral meta-guards (gate wiring, render drift, PR body, guard liveness, admission ratchet, expiring register schema) into `lvlup-sw/.github` composite actions, which already follow the house style of dependency-free Python with fixture tests. Last, ship the TypeScript engines as `@lvlup-sw` packages, and map each pattern onto `Lvlup.Build`/TUnit for .NET and PSRule/Conftest for Bicep/Terraform. Do not adopt Exarchos-the-product as the org's enforcement layer for .NET or IaC teams until issue lvlup-sw/exarchos#1540 lands.

**Evidence base.** Eight readers read the tree statically. Nobody ran a vitest suite, so every statement here about a vitest-hosted guard passing or failing rests on reading the code and CI wiring, not on observation. A few read-only CLI gates were run (the `withSession` gate, `check-type-debt.mjs`, the cast census via `tsx`, `check-no-duplicate-suites.mjs`, `check-measured-premises.mjs`, `pin-trust-root.mjs --check`, `check-gate-runner-ownership.mjs`), and the report says where. Paths link into `lvlup-sw/exarchos` at `8a047d8c9`. A second reader re-checked six claims against the tree: the vacuous `withSession` gate and its stale `src/event-store/` exemptions, the `task 018a` ordinal escape, `state-machine.ts:852`, the npm `files` list, the uncollected `entrypoint-predicates.selftest.test.ts`, and the missing `.github/dependabot.yml`.

## One required check rolls up a guard stack built from data files

The policy catalog below is organized by domain. Each table gives the rule and why it exists, the enforcer and when it runs, how baselines, exemptions and self-proof work, and the known holes. All of it hangs off one trigger path. `main` is protected by ruleset `default` (id 11581356), whose only required status check is `CI Gate`, with strict mode, squash-only merges and organization-admin bypass ([ruleset 11581356](https://api.github.com/repos/lvlup-sw/exarchos/rulesets/11581356)). The classic branch protection that also exists requires nothing and misleads anyone who reads it. `CI Gate` is the verdict mode of the org `ci-lanes@v1` action over seven jobs (`plan`, `test-root`, `test-mcp`, `test-windows-root`, `grep-gates`, `outcome-tests`, `e2e-process`). It fails unless every covered job succeeded or was skipped on a lane the planner reported as exactly `"false"`, and an indeterminate planner is never a pass ([ci-lanes action](https://github.com/lvlup-sw/.github/blob/main/actions/ci-lanes/action.yml)). Anything outside that rollup is advisory, however it is labeled. That includes PR Body Check, Eval Gate, Benchmark Gate, the Windows core suite, `binary-matrix`, `startup-budget`, `lanes-check` and every release job.

### Comments and prose: one policy datum, four ESLint rules, a shrink-only fingerprint baseline

This is the most fully engineered subsystem. One JSON file declares every pattern, check, threshold and exemption. A fail-closed loader validates it. One analysis function serves the ESLint rules, the CI gate, the baseline tools and the precision sampler. The baseline is keyed by content hash and admitted against the PR base. The rollout record shows what the system can do. The baseline went from about **36,000 grandfathered blocks to 60 blocks in 16 files** in about a week, through 23 directory-disjoint cleanup waves (tracker [#1946](https://github.com/lvlup-sw/exarchos/issues/1946), [PR #1936](https://github.com/lvlup-sw/exarchos/pull/1936)).

### Documentation and instruction files: truthfulness is checked, prose quality is not

Every claim CLAUDE.md makes about an enforced rule must name a live enforcer, which turns the agent instruction file into a checked contract. CLAUDE.md breaks its own contract in one place. It states four skill-frontmatter rules, and **none of them is checked repo-wide in CI**.

### Lint and types: strict compiler flags plus two ratchets, and no typescript-eslint preset

Exarchos chose strict `tsc` flags, a few targeted syntax bans and count ratchets over a broad lint preset. The shared [`eslint.config.js`](https://github.com/lvlup-sw/exarchos/blob/8a047d8c9d56c6bf34fc12a6f358f939cf689774/eslint.config.js) is "rule-only, with no recommended set". No `@typescript-eslint` rule is on, and CI has no `npm run lint` step at all. The shared config runs only as a side effect of `lint:comments`. CLAUDE.md says "no `any`", and three mechanisms carry that rule: implicit `any` through `strict`, `as any` through a budget of 0 in the cast census, and nothing at all for explicit `: any` annotations or `@ts-expect-error`. Today the tree has 0 explicit annotations in `src` and 52 `@ts-expect-error` in tests, so a hard ban is cheap.

The CI meta-layer is the most exportable part of the repo. Release-artifact integrity is strong. Every publish job needs a trust-root gate (`tools/release/pin-trust-root.mjs --check`), which the audit ran and saw exit 0. npm publishes through OIDC trusted publishing with SLSA provenance ([npm 2.12.1](https://registry.npmjs.org/@lvlup-sw%2fexarchos/2.12.1)). The repo built a non-short-circuiting runner ([`tools/audit/gates/run-validate.mjs`](https://github.com/lvlup-sw/exarchos/blob/8a047d8c9d56c6bf34fc12a6f358f939cf689774/tools/audit/gates/run-validate.mjs), which asserts executed equals declared), and CI runs only its `--list` mode.

## Seventeen guard techniques reduce to four questions

The patterns matter more than the rules, because they transfer to any language. The Exarchos incident notes and the org's `verify-code` skill state the root principle: "A guard's verdict and its coverage are independent. Absence assertions, exception allowlists, and glob-driven censuses all pass hardest when they read nothing." During the structure refactor, seven guards were found "lying rather than broken". One of them was a "no test is lost" oracle that was "structurally incapable of failing" over 1,147 files because it filtered its own keys. Each technique below answers one of four questions. *Did it look?* *Can it fail?* *Does a failure reach a merge decision?* *Is every exception visible, owned and temporary?*

The meta-guard stack has five layers. Each gate has a seeded self-test (37 `tests/scripts/*.test.sh` in grep-gates). Guard *scope* is proven live (guard-liveness checks 23 surfaces in 8 kinds, and depcruise rule liveness checks each alternation member directory). Guard *wiring* is proven reachable and failable (enforcer wiring, guard inventory, validate runner, tier contract). Tests are policed (suite invariants, inventory, protected suites). Production composition is proven to reach the declared controls (reachable controls). The stack is strongest where the subject is a config the repo can parse, such as globs, workflow YAML, npm scripts and CODEOWNERS. It is weakest where the subject is semantics, such as reachability or prose coherence. Two holes sit at the base of the stack. **No guard requires a gate primary to have a seeded self-test**, so layer 1 rests on convention, and the vacuous Gen-1 gates show what convention delivers. **The enforcer recognizer is name-scoped** to `tools/audit/gates/(check|lint)-*`. That leaves `validate-*.sh`, `tools/audit/core/*-guard.ts`, [`tools/audit/check-base-substrate.ts`](https://github.com/lvlup-sw/exarchos/blob/8a047d8c9d56c6bf34fc12a6f358f939cf689774/tools/audit/check-base-substrate.ts) and `protected:guard` outside it. The next likely class of vacuity is truth held outside the repo: required checks in GitHub settings, the mounted `lvlup-sw/docs` corpus, and the PATH binary that the `process` tier tests.

## Conclusion

The audit changes where the value sits. Exarchos's strength is not that it has many rules. It insists that each rule produce evidence of its own coverage, and it built a second layer of guards to keep the first layer from going quiet. The same repo shows that this discipline decays where no meta-guard requires it. The vacuous Gen-1 gates are not an accident. They are what an un-audited convention produces after a refactor. So the first thing to export is the meta-guard that makes self-tests and denominators mandatory, before any individual linter. That piece is language-neutral, fits the existing `.github` action style, and helps the Bicep and Terraform teams as much as the TypeScript ones, because their policy also lives in workflow steps.

The second lesson concerns the line between repo CI and product governance. Exarchos's own CI enforcement is mature and structural. The governance it imposes on consumer repos is structural only at the task-completion and settlement core, and it is agent-cooperative at review and PR creation. It also cannot yet run on .NET under TUnit or on pure IaC repos. For the org, that argues for putting enforcement in CI through shared actions and packages now, and treating Exarchos workflows as an accelerator on top, not as the control plane, until lvlup-sw/exarchos#1540, lvlup-sw/exarchos#1927 and the admission cutover land. The open risk the org can close and a single repo cannot is truth held outside the tree. Branch-protection required checks, mounted docs corpora and installed binaries are invisible to every in-repo guard. An org-level action with rights to read rulesets is the natural place to verify them.
